## 1. Question

Une image unique multirôle, Compose, Caddy et l'interface statique s'installent-ils simplement ? Les secrets peuvent-ils être déchiffrables par le worker seul (DR6) ?

## 2. Critères de réussite

Les trois critères décisifs sont ceux de la roadmap, sans changement de seuil. Le protocole (§3) précise seulement comment chacun est mesuré.

| # | Critère | Seuil | Source |
|---|---|---|---|
| C1 | Installation sur un VPS vierge 2 vCPU / 4 Go en suivant la seule documentation | **≤ 15 min**, sur la plus lente des exécutions valides | `ROADMAP.md` §5.1 |
| C2 | Mise à jour avec migration, puis retour arrière, selon la documentation | Montée **et** descente réussies ; données de contrôle **identiques** avant et après ; scénario joué en CI et une fois sur le VPS | `ROADMAP.md` §5.1 ; plan d'É0 S6.4 |
| C3 | Le processus API ne peut pas déchiffrer un secret chiffré par clé publique | Tentative de déchiffrement dans le conteneur API : **échec** ; clé privée **absente** de l'image, du conteneur API et de son environnement ; le worker déchiffre le même secret | `ROADMAP.md` §5.1 ; plan d'É0 S6.5 ; `RISKS.md` DR6 |

**Vérifications de conformité** (« fini quand » du plan, sans seuil chiffré) : l'image démarre les trois rôles `api`, `worker` et `scheduler` ; Node.js est absent de l'image finale ; les processus tournent sous un utilisateur non root ; `docker compose up` sert l'interface et `/health` en HTTPS local. Une vérification manquée est notée dans la conclusion ; elle ne fait pas échouer S6 à elle seule, mais elle doit être corrigée avant la fin d'É0.

**Mesures informatives** (aucun seuil, elles alimentent S1 et B09) : taille de l'image compressée et décompressée, durée de construction locale, mémoire au repos de chaque conteneur, délai entre `docker compose up` et l'état « sain » de tous les services.

### 3.3 C1 : installation chronométrée

1. **Avant le chronomètre** (hors mesure) : création du VPS avec l'image du système proposée par le fournisseur, sans mise à jour préalable, accès SSH par clé ; enregistrement DNS de type A créé et propagé. Sans nom de domaine, un nom `<ip>.sslip.io` est utilisé, et l'écart est noté.
2. **Départ** : première commande de la documentation, tapée dans la session SSH.
3. **Inclus** : installation de Docker Engine selon la documentation, récupération des fichiers de déploiement, génération de la configuration, obtention de l'image, démarrage, migrations, certificat TLS.
4. **Obtention de l'image** : on mesure le chemin que la documentation décrit au moment de la mesure. Si un registre a été accepté, c'est un téléchargement ; sinon, c'est une construction sur le VPS depuis le dépôt. Le seuil reste 15 minutes dans les deux cas. Le rapport indique le chemin mesuré.
5. **Arrivée** : depuis une autre machine, `curl -fsS https://<domaine>/health` renvoie 200 avec la base joignable, `https://<domaine>/` renvoie la page de l'interface, et `docker compose ps` montre tous les services sains.
6. **Validité** : une commande hors documentation, ou une correction à la main, invalide l'exécution. La documentation est alors corrigée, le VPS détruit et recréé, puis l'exécution reprise. Le temps passé à ces reprises compte dans la durée maximale de S6.
7. **Répétitions** : au moins deux exécutions valides, chacune sur un VPS recréé. Le verdict porte sur la plus lente.
8. **Relevé** : horodatage du début et de la fin, journal de la session SSH (`script`), qui a exécuté la procédure, version du système, taille de l'image téléchargée ou durée de construction.

### 3.4 C2 : mise à jour et retour arrière

1. Version N de l'image : migration `0001`. Version N+1 : migration `0002` additive (une table ou une colonne), avec sa fonction de descente.
2. Données de contrôle insérées en version N ; empreinte calculée par une requête sur les tables de N (`md5` de la sérialisation triée).
3. **Montée** de N à N+1 selon la documentation : sauvegarde automatique de la base avant migration (`ARCHITECTURE.md` §20.4), migration jouée par le rôle `migrate`, redémarrage. Vérification : `/health` annonce la révision `0002`, empreinte identique.
4. **Descente** de N+1 à N selon la documentation : descente Alembic jouée avec l'image N+1, puis retour à l'image N. Vérification : `/health` annonce la révision `0001`, empreinte identique. La restauration de la sauvegarde est documentée comme second recours et jouée une fois.
5. Le scénario est automatisé dans la CI à chaque demande de fusion touchant `deploy/` ou `backend/migrations/`, et joué une fois à la main sur le VPS après C1.

### 3.5 C3 : séparation des secrets (DR6)

1. Paire de clés générée à l'installation par le script de configuration. La clé publique est fournie à l'API ; la clé privée est un fichier monté **dans le seul conteneur worker**, jamais dans l'image ni dans une variable d'environnement.
2. Schéma hybride avec `cryptography` : échange X25519 éphémère, dérivation HKDF-SHA256, chiffrement AES-256-GCM, avec un identifiant de clé pour la rotation. Il reste compatible avec l'enveloppe d'ADR-11 (une clé de données par espace viendra en É1).
3. **Tests en CI** (unitaires) : aller-retour chiffrement / déchiffrement ; échec sur texte chiffré altéré ; échec avec une autre clé privée ; le module de l'API n'expose aucune fonction de déchiffrement (vérifié par un contrat `import-linter` ou un test d'architecture).
4. **Test de bout en bout** sur la pile Compose (CI et VPS) :
   - l'API reçoit un secret et le stocke chiffré ;
   - dans le conteneur API, un script tente de le déchiffrer avec tout ce que le conteneur contient : il doit échouer faute de clé ;
   - une recherche de l'empreinte de la clé privée dans le système de fichiers et l'environnement du conteneur API ne trouve rien ;
   - `docker compose config` ne montre la clé privée dans aucun service autre que le worker ;
   - une tâche du worker déchiffre le même secret et renvoie son empreinte, qui doit égaler celle du secret d'origine.
5. Hors protocole : une compromission de l'hôte ou du démon Docker donne accès à tous les conteneurs. DR6 protège contre la compromission du processus API, pas contre celle du serveur (`RISKS.md` §4.12).

### 3.6 Hors périmètre de S6

Signature des images (cosign) et SBOM, image `arm64`, haute disponibilité, sauvegardes planifiées, assistant Web d'installation (F-ADM-01), RLS et rôles PostgreSQL séparés (S1 et B05), file de tâches réelle (S2 : le worker de S6 se contente d'une boucle minimale qui prouve le rôle et le déchiffrement). Podman est essayé une fois sur le VPS si le temps le permet, sans seuil.

### 3.7 Si échec

Colonne « Si échec » de la roadmap : DR6 retombe sur ADR-11 tel quel (clé partagée), le risque R-S03 est recoté et une révision de TC-13 est soumise à Joël. Un échec de C1 seul ouvre un ADR « proposé » sur la forme de livraison (TC-13, DT4) ; il ne bloque pas S1.
