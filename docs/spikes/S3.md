## 3. Protocole

### 3.1 Corpus (S3.1)

30 documents, versionnés dans `spikes/s3-document/corpus/` sous licence **CC0-1.0**, écrits pour cette preuve, sans aucun texte repris d'un tiers.

| Groupe | Nombre | Forme d'entrée | Ce qu'il éprouve |
|---|---|---|---|
| Collés | 10 (5 « Word », 5 « Google Docs ») | HTML de presse-papiers reproduisant le balisage connu de ces logiciels : styles `mso-*` et commentaires conditionnels pour Word ; `<b style="font-weight:normal" id="docs-internal-guid-…">`, `<span style>` imbriqués et listes à `aria-level` pour Google Docs | Le nettoyage au collage |
| Sorties IA | 10 | Markdown balisé restreint (`TECH_CHOICES.md` §10.3), avec des marqueurs de référence de source | La conversion déterministe Markdown restreint → JSON |
| Rédigés | 10 | JSON du format directement | Les cas limites : listes imbriquées, citation en fin de document, lien dans un titre, caractères spéciaux, document très court, document long |

Les collages sont **reproduits**, et non capturés dans Word et Google Docs. Si Joël fournit des collages réels avant la première mesure, ils remplacent les reproduits en nombre égal ; le rapport dira lesquels ont servi.

Chaque document du corpus porte au moins 2 sources, un lien, un titre et une citation. Ses éléments attendus sont listés dans un fichier `expected.json`, écrit à la main avant la mesure.

### 3.2 Format et rendu (S3.2, S3.3)

- **Schéma** « Document plateforme v1 » en JSON Schema, publié dans `spikes/s3-document/`. C'est un schéma ProseMirror : un nœud `doc` avec `version_schema`, des blocs portant un `id` stable et une `origine` (`ia`, `ia_modifie`, `humain`), une marque de référence de source, et une citation typée dont l'attribut `source` est obligatoire.
- Le **bloc Sources** et la **mention IA** ne sont pas saisis : le rendu les insère à partir des références et de la part d'IA (`ARCHITECTURE.md` §14.5).
- **Rendu Python** JSON → HTML maîtrisé. **Conversion** Markdown restreint → JSON. **Nettoyage** HTML collé → JSON : il fait partie de l'éditeur, et il est aussi réécrit en Python pour la relecture des CMS.

### 3.3 C3 : concordance (S3.4, S3.5)

- L'éditeur est exécuté sans navigateur, dans Node 24, avec un DOM simulé. Pour Tiptap, le schéma du projet est déclaré en extensions, puis `generateHTML(json)`. Pour BlockNote, le JSON est converti en blocs, puis rendu en HTML. On compare au rendu Python du même JSON.
- **Normalisation** fixée d'avance, appliquée aux deux sorties : arbre HTML reparsé, attributs triés, espaces blancs repliés, attributs `data-*` propres à l'éditeur retirés, entités normalisées. Rien d'autre.
- Le **collage** est éprouvé dans l'éditeur : le HTML collé passe par le nettoyage de l'éditeur, et le JSON obtenu doit être valide selon le schéma.

### 3.4 C1, C2 : aller-retour (S3.6)

- **WordPress** (dernière version stable, et la version majeure précédente pour S7) et **Ghost** (dernière version stable) en conteneurs sur la VM du NAS, avec les images officielles.
- Chaque document est rendu en HTML par le moteur Python, puis publié en brouillon. WordPress le reçoit par l'API REST, dans le champ `content`. Ghost le reçoit par l'Admin API avec `?source=html` : Ghost convertit alors le HTML dans son propre format (Lexical).
- **Relecture** : on lit le contenu rendu renvoyé par l'API (`content.rendered` pour WordPress, `html` pour Ghost). On en extrait les éléments obligatoires avec le même analyseur que pour `expected.json`, puis on compare.
- **Taux de conservation par élément** = éléments retrouvés ÷ éléments attendus, sur tout le corpus, pour chaque CMS. Un élément est retrouvé si son texte, sa cible (pour un lien) et sa nature (niveau de titre, citation, lien) sont identiques après normalisation.

### 3.5 C4 : décision (S3.7)

Critères écrits d'avance : licence des paquets réellement utilisés, conformité au schéma du projet (nœuds et attributs personnalisés), concordance (C3), qualité du nettoyage au collage, taille du code livré au navigateur, maturité.

### 3.6 Exécution

Corpus, schéma, rendu, conversion et concordance tournent sur le poste ou en CI ; le Node de l'éditeur tourne en conteneur. WordPress et Ghost tournent sur la VM, détachés. Résultats JSON dans `spikes/s3-document/results/`.

### 3.7 Si échec

Colonne « Si échec » de la roadmap : révision de TC-07 soumise à Joël avant tout code de rédaction. Un échec de S3 suspend S7 jusqu'à sa décision (plan d'É0 §2).

**Écarts au protocole**
- `expected.json` n'a pas été écrit à la main. Il est dérivé de la forme abstraite de chaque document, celle qui sert aussi à produire le JSON, le Markdown et le HTML collé. Il ne vient donc ni du rendu ni de l'analyseur : un défaut de la chaîne ne peut pas se cacher.
- Les collages sont reproduits, comme le prévoyait le §3.1 : Joël n'a pas fourni de collage réel.
- La concordance de Tiptap à 100 % tient à la construction : les extensions de l'éditeur reproduisent le rendu Python. La preuve établit que ce miroir est possible et vérifiable automatiquement, pas qu'il est gratuit.
- Le premier lancement de l'aller-retour a échoué à l'écriture de son fichier de résultats, faute de droits sur le dossier. La mesure retenue est le lancement suivant, identique.

Fichiers bruts : `spikes/s3-document/results/` (`roundtrip-*.json`, `concordance-*.json`).

## 5. Conclusion

**Succès.** Le format « Document plateforme v1 », rendu par le moteur Python, passe intact par WordPress (versions 7.1 et 6.9) et par Ghost : titres, liens, citations avec leur source, bloc Sources et mention IA, pour 100 % du corpus. Tiptap rend le même document à l'identique, à la normalisation près. BlockNote, par construction, ne le peut pas sans réécrire son modèle. La décision est Tiptap, avec un nettoyeur de collage à écrire pour l'éditeur.

## 7. Ce que la preuve n'a pas couvert

- De vrais collages de Word et de Google Docs : les reproductions suivent le balisage connu, sans ses variantes réelles (tableaux, images collées, styles de liste multiples).
- Le calcul de la part d'IA sur des scénarios d'édition (division, fusion, collage, réécriture) et la comparaison de versions, annoncés dans `TECH_CHOICES.md` §10.3 mais hors des seuils de la roadmap : à couvrir par des tests de propriétés avant le code de l'éditeur.
- Le rendu de l'éditeur dans un vrai navigateur, l'édition interactive et la taille du code livré.
- Les extensions de sécurité ou de SEO de WordPress, qui peuvent filtrer le contenu : ce sera S7, avec l'hébergement mutualisé.
- La conservation des classes CSS du projet par Ghost, qui n'est pas exigée : l'extraction ne repose que sur le contenu.
